# Kosti — контроль качества DXA

обучены и проверены ResNet18 baseline и вариант с балансировкой; выполнено сравнение с DINOv2. Рабочий ResNet18-комплект: `artifacts/balanced-baseline-20260927/final/final/manifest.json`. Macro-F1 нарушений 0.290, F1 общего решения 0.444, ROC-AUC 0.652 на внутренней групповой кросс-валидации. Все 499 файлов обработаны без технических ошибок. Модель остаётся исследовательской: слабое распознавание оси и отсутствие внешней валидации не позволяют считать качество задачи достигнутым. Метрики, запуск и оставшиеся критерии: [docs/RELEASE.md](docs/RELEASE.md).

## Быстрый старт

Python 3.11–3.13. Виртуальное окружение и основные зависимости:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install '.[test]'
.venv/bin/python -m pytest -q
.venv/bin/kosti audit data/Исследования --labels data/разметка.xlsx --output artifacts/audit.json
.venv/bin/kosti serve
```

В режиме без модели доступны локальная страница по `http://127.0.0.1:8000/`, проверка живости и OpenAPI по `/docs`. Готовность к медицинскому анализу включается только с явным качественным модельным комплектом:

```sh
.venv/bin/python -m pip install '.[ml,test]'
.venv/bin/kosti batch input.zip --model artifacts/quality/manifest.json --output outputs/run1
.venv/bin/kosti serve --model artifacts/quality/manifest.json
```

В примерах замените `artifacts/quality/manifest.json` на путь к рабочему комплекту выше или `models/manifest.json` из релизного архива. Без модели `/ready` и обработка возвращают 503. Структура и процедура подготовки описаны в [ML_HANDOFF.md](docs/ML_HANDOFF.md).

## API и пользовательский сценарий

- `GET /` — локальная страница загрузки и просмотра. При подключённой модели можно выбрать DICOM/ZIP, увидеть результат и диагностику каждого файла, открыть уменьшенное изображение и скачать CSV.
- `GET /health` — живость процесса.
- `GET /ready` — готовность загруженной модели; 503, если модели нет.
- `POST /v1/batch` — multipart-загрузка одного или нескольких файлов под именем `files`: DICOM либо ZIP. Возвращает ZIP с `results.csv` и `diagnostics.json`.
- `POST /v1/review` — та же обработка для интерфейса: JSON со строками результата, диагностикой, уменьшенными PNG-превью и готовым CSV. Временные загрузки удаляются после ответа.
- `GET /docs` — описание схем и интерактивная проверка API.

```sh
curl -f http://127.0.0.1:8000/ready
curl -f -F 'files=@input.zip' http://127.0.0.1:8000/v1/batch -o results.zip
```

Выгрузить результаты, открыть CSV в Excel или прочитать программно. Строка `Failure` требует просмотра соответствующей записи `diagnostics.json`. Повторные пиксели с разными файлами не удаляются из результатов. Неподдерживаемое или повреждённое изображение не останавливает обработку других файлов. Отказ всего запроса применяется к отсутствию модели, нарушению формата запроса и небезопасному/слишком большому архиву.

## Выходной формат

CSV: UTF-8 с BOM, стандартное экранирование полей, следующий порядок колонок:

| Поле | Смысл |
|---|---|
| path_to_study | Путь входного файла; при обработке архива — путь внутри него |
| study_uid | Исходный StudyInstanceUID |
| image_uid | Исходный SOPInstanceUID |
| anatomical_region | `Поясничный отдел позвоночника` или `Проксимальный отдел бедра` |
| quality_class | 0 — нет выявленных нарушений; 1 — найден хотя бы один тип |
| violation_type | Названия типов через `; `; пусто при норме |
| processing_status | `Success` или `Failure` |
| time_of_processing | Секунды обработки изображения |
| quality_prob | Вероятность любого нарушения в диапазоне [0; 1] |

При технической ошибке медицинские поля пустые; известные UID сохраняются, отсутствующие не выдумываются. Вероятность общего качества и отдельные типы — разные выходы модели. В текущей политике бинарный класс определяется порогами типов; общая вероятность сохраняется отдельно для оценки ROC-AUC. Несовпадения исходных экспертных меток требуют отдельной проверки, а не скрытого исправления.

## Данные и модель

Чтение DICOM учитывает rescale/modality LUT, VOI LUT, MONOCHROME1 и padding; сохраняет геометрию оригинального массива. Поддерживается одиночный монохромный кадр. RGB, неподдерживаемый multiframe, отсутствие UID/пикселей и константный полезный кадр отклоняются. Сжатые transfer syntax требуют соответствующего декодера; наличие такого декодера не гарантируется этой базовой поставкой.

В текущем наборе нет PixelSpacing. Физические единицы не подставляются автоматически. Отсутствие spacing не препятствует классификации, но ограничивает геометрические измерения.

Модельный адаптер загружает только локальные веса и явную конфигурацию предобработки. Загрузка не обращается к Torch Hub и не скачивает веса. Модели анатомии и качества имеют разные контракты. Все параметры предобработки и порядок классов фиксируются в manifest.

DINOv2 ViT-S/14 сравнен на тех же фолдах и не включён в сервис: устойчивого улучшения нет. Геометрические модели и внешние наборы в рабочем комплекте отсутствуют.

## Структура и задачи

- `src/kosti/contracts.py` — схема результата и интерфейсы.
- `dicom.py`, `dataset.py` — чтение изображений, аудит и разметка.
- `ml.py`, `evaluation.py` — загрузчики моделей, групповые разбиения и метрики.
- `pipeline.py`, `archive.py`, `api.py`, `cli.py` — обработка, экспорт, API и CLI.
- `tests/` — синтетические тесты без реальных медицинских изображений.

## Развёртывание

```sh
sh scripts/build.sh
sh scripts/run.sh
```

Образ стартует от непривилегированного пользователя. Без модели это доступный диагностический API с отрицательной готовностью. Модельный каталог подключается отдельно только для чтения:

```sh
KOSTI_MODELS_DIR=/absolute/path/to/quality sh scripts/run.sh
```

Стандартная сборка включает CPU-зависимости модели. `scripts/run.sh` использует каталог `models/` из релизного архива либо путь `KOSTI_MODELS_DIR` и завершается понятной ошибкой, если веса отсутствуют. CPU-образ проверен 27 сентября 2026 года на Ubuntu 24.04 x86_64 с Docker 29.1.3: модель загрузилась, `/health`, `/ready`, интерфейс и `POST /v1/review` с DICOM вернули успешные ответы. Публичный демонстрационный стенд: `http://158.160.203.10:8000/`. CUDA-образ и замеры на H200 остаются отдельной задачей; текущий стенд работает на CPU. Контейнеризация не равна подтверждению работы на H200: GPU-прогон и измерение лимита 180 секунд остаются критериями финальной сдачи.

Прямые зависимости закреплены в pyproject.toml, точные транзитивные версии — в `requirements-core.lock`, `requirements-test.lock` и `requirements-ml.lock`. Для повторения проверенного окружения устанавливать соответствующий lock перед `pip install --no-deps .`. Linux/CPU-профиль проверен; Linux/CUDA-профиль должен быть отдельно проверен перед финальной сдачей.

Системные требования для CPU-инференса (Python 3.11–3.13, Linux/Unix или Docker):

| Ресурс | Минимальная рекомендуемая конфигурация | Конфигурация с запасом |
|---|---|---|
| CPU | 2 ядра x86_64 или ARM64 | 4 ядра |
| RAM | 2 GiB для контейнера и память для ОС | 4 GiB для контейнера |
| GPU | Не требуется для текущего ResNet18 | Не требуется; CUDA/H200 отдельно не проверены |
| Диск | 5 GiB для окружения/образа и модели, плюс входные данные | 10 GiB и место для рабочих пакетов |
| Временное хранилище | До 5 GiB на большой API-пакет | 10 GiB для одного пакета; больше при параллельных запросах |

Это эксплуатационные рекомендации, а не измеренный нижний предел ресурсов. Проверенный серверный профиль: Ubuntu 24.04 x86_64, CPU, лимит контейнера 2 GiB; одиночный smoke-тест использовал около 278 MiB. Локальный последовательный прогон 499 файлов потребовал около 397 MiB пикового RSS. Для больших архивов нужны место под загрузку и распаковку, а при `/v1/review` — дополнительная память для превью. Число CPU-ядер и дисковый минимум отдельно не бенчмаркались; время на H200 не подтверждено.

## Известные ограничения

- Качество измерено только внутренней кросс-валидацией; независимой клинической валидации нет, распознавание ряда нарушений слабое.
- Индексация 252 изображений выполнена ИИ, требует независимой проверки; сторона 19 изображений бедра неизвестна, спорные метки маскируются.
- Аудит выявляет метки и противоречия, но не исправляет их за эксперта.
- Геометрия оси/ROI, полноценный просмотр снимков, DICOM SR и коррекция разметки пока не реализованы.
- Проекция передаётся в диагностике как значение `ViewPosition` из DICOM с источником `DICOM.ViewPosition`; при отсутствии или неизвестном значении — `unknown`. Определение проекции по самому изображению пока не обучено. Направление луча не выводится из имени файла или ориентации плоскости.
- Валидация должна группировать исследования и повторы; общий PatientID в предоставленном наборе не годится для разделения пациентов.

Реальные данные, исходные архивы, локальные веса и результаты аудита исключены из Git. Финальные веса и проверка офлайн-запуска получены локально; скрипт `scripts/package_release.py` собирает отдельный архив с моделью. Linux/Docker CPU-деплой подтверждён; GPU/H200 и независимая клиническая валидация остаются открытыми.

## Подготовка разметки и оценка без обучения

Команды `kosti annotation-template`, `kosti prepare-folds` и `kosti evaluate`
создают шаблон ручной разметки, фиксируют групповые фолды и оценивают готовые
вероятности. Подробный порядок и формат файлов: [docs/PREPARATION.md](docs/PREPARATION.md).

Скрипт ResNet18 baseline: `kosti training-config` и `kosti train`.
По умолчанию выполняется только проверка; обучение требует `--execute`.
Конфигурация, локальные веса и протокол: [docs/TRAINING.md](docs/TRAINING.md).

Локальная галерея ручной разметки: `kosti review-gallery`; инструкция в
[docs/PREPARATION.md](docs/PREPARATION.md). Для подготовленного приватного
запуска на Kaggle после проверки меток и изображений см.
[docs/KAGGLE.md](docs/KAGGLE.md). Ключ Kaggle и данные не коммитятся.
