# ResNet18 baseline: скрипт подготовлен, обучение не запускалось

Этот этап добавляет воспроизводимый entrypoint. Он не подтверждает качество
модели. По умолчанию `kosti train` проверяет входы без оптимизации и без создания
каталога результатов. Нужны установленные зависимости `requirements-ml.lock`
и текущая версия пакета; подготовка разметки описана в [PREPARATION.md](PREPARATION.md).

## Входы

1. Проверенный `folds.json` из `prepare-folds`, с обеими анатомическими областями.
2. Каталог исходных DICOM, относительно которого сохранены пути в манифесте.
3. Локальный torchvision ResNet18 ImageNet **state_dict** с исходной головой на
   1000 классов. Не whole-model pickle, не anatomy-checkpoint на 2 класса, не
   готовый quality-bundle. Происхождение весов необходимо проверить отдельно:
   SHA256 фиксирует содержимое, но сам по себе не доказывает обучение на ImageNet.

Код не скачивает веса. Команда генерации конфигурации записывает SHA256 уже
имеющегося файла. Если готового ImageNet checkpoint нет, эту зависимость нужно
подготовить отдельно; исходный `model_classifaer.pth` подставлять нельзя.

## Конфигурация и проверка без обучения

Из корня репозитория на машине, где будет запускаться обучение:

```bash
python -m kosti.cli training-config artifacts/folds.json \
  --data-root ../data/Исследования \
  --initial-weights artifacts/imagenet-resnet18.pth \
  --output artifacts/runs/resnet18-cv \
  --config artifacts/train.json

python -m kosti.cli train --config artifacts/train.json
```

Генератор записывает абсолютные локальные пути, CPU, 10 эпох, batch size 16,
learning rate 0.001, weight decay 0.01, seed 42, размер 224 и замороженный backbone.
Это исходная конфигурация эксперимента, а не подобранные параметры.
Перенос на другую машину требует актуальных путей. Неизвестные поля и опечатки
в конфигурации отклоняются. Существующий JSON не перезаписывается.

Валидация проверяет схему, источник меток, принадлежность каждой копии фолду,
отсутствие утечек по исследованиям, nullable-метки и противоречия качества.
В каждой обучающей части должны быть обе области и хотя бы один известный
позитив и негатив для каждого из семи выходов. Отсутствие классов блокирует
обучение; нельзя получать формально готовые, но не обученные на разметке головы.
Редкие метки могут потребовать другого заранее зафиксированного группового
разбиения или дополнительной разметки. Нельзя менять фолды по полученным метрикам.

Для каждого выбранного уникального изображения повторно проверяются UID и
pixel_hash, выполняется предобработка. Затем проверяется совместимость локального
checkpoint. Это проверка входов; доступность целевого GPU и расход памяти ею не
подтверждаются. При наличии выходного каталога требуется новое имя запуска.

## Позднее: явный запуск обучения

Следующая команда **запускает оптимизацию**. В текущем этапе она не выполнялась:

```bash
python -m kosti.cli train --config artifacts/train.json --execute
```

Для GPU изменить `device` на `cuda` и перед запуском задать:

```bash
export CUBLAS_WORKSPACE_CONFIG=:4096:8
```

Используются детерминированные операции PyTorch; неподдерживаемая операция
завершит запуск ошибкой вместо незаметного отключения проверки. Одинаковый seed
не обещает побитовой идентичности между разными версиями библиотек и устройствами.
MPS пока не поддерживается.

Каждый fold начинает с тех же исходных весов и новой головы, с записанным правилом
seed = базовый seed + номер запуска. В обучении используются только остальные
фолды. CE обучает анатомию, masked BCE — пять нарушений и две метки качества;
неизвестные значения не участвуют в BCE. По умолчанию обучается только голова;
backbone и статистики BatchNorm заморожены. Для полного fine-tuning изменить
`freeze_backbone` на `false` до эксперимента. Последний singleton-batch объединяется
с предыдущим; ни один пример не отбрасывается.

Случайные повороты, обрезки, балансировка классов и калибровка не добавлены.
Предобработка совпадает с инференсом: minmax, letterbox, RGB и явные mean/std.
Эпохи фиксированы заранее; отложенный fold не используется для early stopping,
выбора checkpoint, порогов или настройки гиперпараметров. Порог baseline — 0.5.
Для настройки параметров потребуется отдельная внутренняя валидация.

## Результаты

- `config.json`, `splits.json`, `run.json`: разрешённые пути, параметры,
  исходное разбиение, checksum манифеста, версия PyTorch и состав запусков.
- `fold-N/weights.pth`, `manifest.json`, `history.json`: финальное состояние
  соответствующего fold и журнал training loss по эпохам.
- `oof.csv`: вероятности для каждого sample, полученные только на отложенном fold;
  совместим с командой `evaluate`.
- `metrics.json`: фиксированные метрики при пороге 0.5; отдельная macro-F1 пяти
  нарушений находится в `violations.macro_f1`.
- `completed.json`: весь запуск завершён. При ошибке — `failed.json` и частичные
  результаты; их нельзя считать завершённым экспериментом. `run.json` фиксирует
  начало запуска, терминальный статус задаётся этими отдельными файлами.

Bundle имеет тот же порядок девяти выходов и ту же schema v1, что и API.
Он технически пригоден для загрузки сервисом, но требует независимой оценки;
экспорт не означает медицинскую валидацию. Никакие тестовые веса не публикуются.

## Финальная модель после выбора протокола

Создать отдельную конфигурацию с `training-config --mode final`, выбрать новый
каталог результатов и зафиксировать параметры, выбранные ранее без внешней утечки.
После проверки запускать той же командой с `--execute`. Все samples участвуют
в обучении, bundle записывается в `final/`. OOF и метрики для финального запуска
не создаются: оценивать его на обучающих изображениях как независимую модель нельзя.
Отдельный независимый holdout и клиническая проверка остаются задачами команды.

## Что фактически проверено

Тесты проверяют dry run, защиту разбиений, изменённые DICOM, совместимость bundle,
заморозку BatchNorm, полное покрытие OOF, отдельную инициализацию каждого fold,
отметки завершения/сбоя и режим final. В тестах оркестрации `fit_model` заменён
заглушкой; шаги оптимизатора не выполняются. Работоспособность длительного
обучения, GPU, сходимость и качество модели пока не подтверждены.
# Обновление 27 сентября 2026

Реальное обучение и сравнение выполнены, результаты: [RELEASE.md](RELEASE.md).
Опциональное поле конфигурации `balance_classes: true` включает веса
negative/positive отдельно по каждому из семи бинарных выходов, рассчитанные
исключительно по обучающей части текущего фолда. По умолчанию поле false,
старые конфигурации сохраняют поведение baseline.

При `freeze_backbone: true` признаки кешируются один раз в памяти на фолд:
encoder и BatchNorm остаются в eval, обновляется только голова. Аугментаций
в данном протоколе нет, поэтому повторять один и тот же encoder-forward каждую
эпоху не требуется. Кеш между фолдами не используется.

`scripts/compare_dinov2.py` принимает локальный официальный checkout DINOv2,
его веса, существующую конфигурацию и новый каталог результата. Скрипт не
скачивает файлы. Для воспроизведения текущего сравнения нужен upstream commit
`7764ea0f912e53c92e82eb78a2a1631e92725fc8`; SHA256 весов записан в protocol.json.
Он выдаёт OOF и линейные головы, не production-bundle для текущего API.
