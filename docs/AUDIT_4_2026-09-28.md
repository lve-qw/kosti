## Итог

Программный контур сделан очень хорошо: чтение DICOM, безопасная распаковка ZIP, изоляция ошибок по файлам, контракт CSV, API, веб-интерфейс, Docker, lock-файлы, CI/CD, честная документация ограничений. По критериям 8.2 и 8.3 проект сильный.

Главные потери баллов сейчас не в коде, а в четырёх местах:

1. Лучшая модель обучена, но не выпущена: сервис, релизы, README и презентация используют более слабую модель (224 px).

3. `quality_prob` и `quality_class` противоречат друг другу в 23% строк.
4. Проекция не определяется (обязательная функция 2.2), дополнительный функционал 2.6 не реализован, хотя тепловая карта для ResNet18 делается за полдня.

CI для F1 почти не пересекаются, прирост устойчивый. Финальный бандл `artifacts/resolution448-final-20260928/final/manifest.json` уже обучен и прошёл benchmark и runtime-проверку: 499 файлов, 0 ошибок, результаты воспроизводимы, максимум 34.5 с на исследование при холодном старте. Однако:

Что сделать: `promote-model.sh` на сервере → `package_release.py` с новым manifest → обновить README, RELEASE, DEMO и презентацию. В тексте честно указать, что выбор разрешения сделан на тех же фолдах (оптимистичное смещение), но разница больше ширины CI.

### 2. Контейнер, который работает у организатора без команды

Сейчас `sh scripts/build.sh && sh scripts/run.sh` собирает образ **без torch и без весов**: `INSTALL_ML=0` по умолчанию, а веса монтируются отдельно. Эксперт получит `/ready` = 503 и ни одной строки CSV. Это прямой риск по 7.2 («устойчивая пакетная обработка закрытого набора», «обученная модель и все веса», «скрипт сборки и запуска»).

Что сделать:

- Финальный Dockerfile (или профиль `final`): `INSTALL_ML=1` по умолчанию и `COPY models/ /models/` с `ENV KOSTI_MODEL_MANIFEST=/models/manifest.json`. Если веса нельзя класть в Git, `build.sh` должен брать их из распакованного релиза и падать с понятной ошибкой, когда их нет.
- Однокомандный пакетный режим без HTTP, например `sh scripts/run.sh batch /data/input /data/output` → `docker run -v input:ro -v output ... kosti batch /input --output /output`, на выходе `results.csv` и `diagnostics.json`. Экспертам это проще, чем multipart-запрос.
- Отдать образ архивом `docker save kosti:final | gzip > kosti-final.tar.gz`: сборка сейчас требует интернета (PyPI, download.pytorch.org), а у проверяющих его может не быть.
- Проверить код возврата: `kosti batch` возвращает 1, если есть хотя бы один Failure. Скрипт организатора может принять это за падение всего запуска. Лучше возвращать 0 и сообщать о сбоях в CSV и диагностике, а ненулевой код оставить только для фатальных ошибок.
- Добавить в README раздел «Запуск для экспертов» из трёх команд.

### 3. Согласовать `quality_prob` и `quality_class`

`quality_class` = OR порогов по типам нарушений, а `quality_prob` = отдельная голова качества. На OOF-предсказаниях resolution448 в **55 из 242 строк (23%)** класс и вероятность противоречат друг другу: например, `quality_class=1` при `quality_prob<0.5`. Организатор будет считать F1 по классу и ROC-AUC по вероятности, а эксперт увидит нелогичные строки.

Быстрая проверка на тех же OOF:

| Скор | ROC-AUC общий | Позвоночник | Бедро |
|---|---:|---:|---:|
| Голова качества (сейчас) | 0.763 | 0.696 | 0.813 |
| max(вероятности нарушений) | 0.761 | 0.610 | 0.858 |
| среднее (голова, max) | **0.787** | — | — |

Вариант: `quality_prob = mean(head, max_violation)`, а при `quality_class=1` поднимать вероятность не ниже порога решения (или порог выбирать на вложенной CV). Итог: одна согласованная величина и не хуже по AUC. Проверять это нужно вложенной CV, а не подбором на тех же фолдах.

### 4. Проекция (обязательная функция 2.2)

Сейчас проекция берётся только из `ViewPosition`; при отсутствии тега возвращается `unknown` и попадает только в `diagnostics.json`. В README сказано, что в наборе нет PixelSpacing; вероятно, ViewPosition тоже часто пуст, и тогда требование формально не выполнено.

Минимум: для DXA стандартная проекция определяется областью (поясничный отдел — прямая задняя AP/PA, проксимальный отдел бедра — прямая AP). Выводить её с источником `protocol_by_region`, если нет тега, и добавить колонку `projection` в конец CSV. Дополнительные колонки допустимы, обязательные девять стоят первыми. Лучше, но дольше: обучить голову сторона/проекция (лево/право бедро как минимум).

### 5. Тепловая карта нарушений (2.6, 8.3, питч)

### 6. DICOM SR с текстом нарушений (2.6)

Простой Basic Text SR через pydicom: область, класс, список нарушений с вероятностями, версия модели и пометка «не является клиническим заключением». Одна функция и тест. Класть в тот же `results.zip`.

### 7. Ось позвоночника: подключить геометрию

Ось — самое слабое место (F1 0.111, AUC 0.548 у resolution448). Эвристика `scripts/check_axis_geometry.py` на тех же 99 снимках даёт **ROC-AUC 0.737**, но F1 0.143 при фиксированном пороге 5°. Сигнал есть, порог 5° на грубой оценке угла слишком строгий. Варианты:

- подавать угол как дополнительный признак в голову оси (конкатенация с эмбеддингом) либо брать OR/максимум с нейросетью;
- подбирать порог угла только во внутренней CV, а в отчёте показывать угол в градусах в диагностике — это объяснимость, которую прямо просит задание («Угол наклона 6,9 градусов»).

Аналогично для бедра: в 4.md даны геометрические правила ROI (3 см сверху и снизу, 2 см сбоку, пиксель 1.05 × 0.6 мм). Кроме того, анизотропный пиксель не учитывается в letterbox-предобработке: снимок сжат по X примерно в 1.75 раза. Стоит проверить ресэмплинг к квадратному пикселю перед resize.

## P2 — полировка

- **H200/целевая конфигурация.** CPU-инференса хватает с большим запасом (≤35 с на исследование против лимита 180 с), GPU не обязателен. Стоит явно написать это в README и замерить хотя бы на CPU-VM, похожей на целевую (44 vCPU). Флаг `--device auto` (CUDA при наличии) — опционально.
- **Минимальная и рекомендуемая конфигурация** (3.1): есть, но с оговоркой «не измерено». Замерить 2 и 4 ядра на 50 файлах и дать числа.
- **README устарел:** «Состояние на 27 сентября», пути к balanced-baseline; комментарий в `.sourcecraft/ci.yaml` говорит «75 тестов», а их 183.
- **Руководство пользователя и руководство по развёртыванию** (раздел 5) разбросаны по README, DEMO, ML_HANDOFF и RELEASE. Нужно собрать два коротких файла `docs/USER_GUIDE.md` и `docs/DEPLOYMENT.md`, на них ссылается жюри.
- **Воспроизводимость сборки:** базовый образ закреплён тегом `python:3.11.11-slim-bookworm`, а не digest; torch ставится без хэшей. Добавить `@sha256:...` к FROM.
- **CI деплоит** только из ветки `codex/output-contract-foundation`. Проверить, что это действительно рабочая ветка, иначе main-коммиты не попадут на стенд.
- **Публичный стенд без аутентификации** принимает медицинские файлы по HTTP. На время защиты поставить basic-auth через nginx или ограничить по IP, после защиты закрыть.
- **Калибровка:** ECE 0.22 у 448. Temperature scaling на OOF — дешёвый выигрыш для Brier/ECE и более осмысленной `quality_prob`.
