# План решения по заданию и выходным данным

## Основной результат

Локальный контейнеризированный сервис принимает DICOM или архив исследований и формирует `results.csv`: одна строка на входное изображение, одна анатомическая область в строке. Весь план ниже строится от заполнения этой таблицы. Исследовательский материал после основного плана — обоснование выбора методов, а не дополнительный обязательный объём разработки.

Срок — 8 дней, GPU есть, эксперта нет. Код решения пока не разрабатывается.

## 1. Контракт выходной таблицы

| Колонка | Требуемый результат | Как получаем | Как проверяем |
|---|---|---|---|
| `path_to_study` | Путь к исходному исследованию или файлу | Для однозначности записываем путь к конкретному входному файлу; в ZIP — относительный путь внутри архива | По строке можно найти исходный файл; пути не являются признаками модели |
| `study_uid` | Идентификатор исследования | Читаем `StudyInstanceUID` из DICOM | Значение совпадает с тегом, не подменено именем папки |
| `image_uid` | Идентификатор изображения | Читаем `SOPInstanceUID` | Результат связан с конкретным изображением |
| `anatomical_region` | `Поясничный отдел позвоночника` или `Проксимальный отдел бедра` | Классификатор области; сначала проверяем имеющиеся веса | Точные строки из задания; никаких суффиксов лево/право и зависимости от имён файлов |
| `quality_class` | 0 — качественное; 1 — есть нарушение | Решение по выявленным нарушениям с порогами, выбранными на валидации | F1, sensitivity, specificity, balanced accuracy; согласованность с `violation_type` |
| `violation_type` | Один или несколько допустимых типов для данной области | Специализированные multilabel-выходы и проверяемые геометрические признаки | Macro-F1 и показатели каждого нарушения; несколько нарушений не сводятся к одному |
| `processing_status` | `Success` или `Failure` | Результат технической обработки файла | Повреждённый файл не останавливает пакет; низкая уверенность модели сама по себе не Failure |
| `time_of_processing` | Время обработки в секундах, Float | Замер чтения, анализа и формирования результата изображения | Дополнительно проверяем суммарное время исследования: не более 180 секунд |
| `quality_prob` | Вероятность наличия нарушения в [0; 1] | Вероятностная оценка общего качества, проверенная на отложенных данных | ROC-AUC/PR-AUC, калибровка; это не вероятность анатомической области |

CSV — основной обязательный экспорт; XLSX можно добавить теми же данными. Для строки с `Failure` сохраняем путь, доступные UID, статус и время; не создаём фиктивные медицинские предсказания. Задание не определяет заполнение остальных полей при Failure: предлагаем пустые значения и фиксируем это в README до подтверждения организатором.

Предлагаемое представление `violation_type`: пустая строка при норме, точное название при одном нарушении, названия через `; ` при нескольких. Разделитель перечня и допустимость пустых полей — наши явно документированные соглашения, не заданные в 4.md требования.

Дубли можно считать один раз с кешированием, но результаты возвращаются для каждого входного изображения/файла с его путём и UID. Удаление дублей при обучении не должно приводить к потере строк при пакетной сдаче.

## 2. Какие именно нарушения выдаёт сервис

| Область | Точное значение `violation_type` | Основание по заданию | План определения |
|---|---|---|---|
| Позвоночник | `Некорректная укладка` | В кадре должны быть верхние края подвздошных костей и половина тела Th12 | Классификация по экспертным меткам + оценка охвата кадра по анатомическим ориентирам |
| Позвоночник | `Не выравнена ось позвоночника` | Допустимый наклон до 5° | Локализация центральной линии и измерение наклона; обучаемая оценка как резерв при ненадёжной локализации |
| Позвоночник | `Присутствуют посторонние предметы` | Посторонние предметы, выраженные артефакты или наложения | Отдельный выход модели по существующей разметке; визуализация подозрительной зоны |
| Бедро | `Некорректная укладка` | Видны большой вертел, шейка и седалищная кость; корректна ротация по малому вертелу | Совместный классификатор обеих сторон; дополнительные признаки анатомии при подтверждённой пользе |
| Бедро | `Некорректная область интереса` | Требования к области интереса и отступам 3 см сверху/снизу, 2 см сбоку согласно заданию | Классификация по готовым ROI-меткам + геометрическая проверка после установления конкретных границ ROI |

Это пять проверок в двух анатомических ветках, а не пять взаимно исключающих классов. Например, позвоночник может одновременно иметь нарушение оси и посторонний предмет. Новые типы вроде «сколиоз», «остеопороз» или «перелом» в итоговый перечень не добавляются.

Отсутствие видимой исходной ROI не исключает обязательный класс из решения: он обучается по выданной экспертной оценке. Ограничение касается точной геометрической интерпретации и проверки неизвестной разметки. Уточнение у организатора идёт параллельно разработке всех обязательных выходов.

## 3. Обратный план от таблицы к моделям

1. **Зафиксировать соответствие входов и строк результатов.** Создать манифест файлов, UID и учебных меток. Учебные дубли объединить. Все изображения одного исследования держать в одной части разбиения.
2. **Получить `anatomical_region`.** Восстановить архитектуру и предобработку текущего чекпойнта, проверить порядок классов и качество. Использовать его, если проверка успешна; иначе переобучить компактную модель. Определение стороны — только внутренняя задача связывания правой/левой учебной метки.
3. **Получить вероятности типов нарушений.** Предобученный энкодер и головы: три для позвоночника, две для бедра. Начальный кандидат — DINOv2; CNN служит сравнительным baseline. Пустые экспертные метки не превращать в нули.
4. **Получить `quality_class` и `quality_prob`.** Бинарную голову обучать по итоговой экспертной оценке, головы типов — по частным признакам. Базовый согласованный бинарный вывод — наличие хотя бы одного выявленного типа; отдельная бинарная вероятность даёт оценку общего риска для AUC. На валидации сравнить варианты согласования. Для трёх конфликтных строк исходной таблицы сохранить обе метки и запросить трактовку; не добавлять выдуманный тип ради согласованности. Окончательную политику зафиксировать до финального обучения.
5. **Усилить обязательные предсказания геометрией.** В первую очередь угол оси, затем охват кадра и ROI. Вводить модуль в решение только при устойчивом улучшении; неопределённая сегментация не должна автоматически означать нарушение.
6. **Получить технические поля.** Добавить изоляцию ошибок по файлам, измерение времени и экспорт. Проверить повторяемость, работу без сети и полный пакетный прогон.
7. **Добавить необязательное объяснение.** UI и визуализация используют уже вычисленные результаты, а не заменяют их. DICOM SR и автокоррекция — только при готовом обязательном контуре.

## 4. Как выбираем решение для максимального конкурсного результата

Основная цель экспериментов — F1 и ROC-AUC определения нарушения качества, отмеченные в задании как приоритетные. Дополнительно оптимизируем macro-F1 типов и полноту успешной обработки. Уменьшение ошибок анатомической области также важно: неправильная область выбирает неправильный набор проверок.

Не обещаем числовой конкурсный балл: формула объединения метрик не дана. Сравниваем модели на одинаковых групповых фолдах и показываем показатели в целом, по области и по типу. Пороги подбираются без использования оцениваемых групп; интервалы — по исследованиям. Измеряем end-to-end качество готовых строк, а не только качество отдельных моделей на правильно выбранных вручную входах.

Порядок вложения времени: корректный CSV и все обязательные классы → честный baseline → повышение F1/AUC → редкие нарушения и macro-F1 → надёжность/скорость → объяснения и демонстрация. Готовые энкодеры и внешние данные — средства улучшить эти выходы, а не отдельная цель.

## 6. Критерии готовности

- Одна строка на входное изображение; строки не теряются из-за дублей, ошибок или низкой уверенности.
- UID взяты из DICOM; модель не использует имена файлов, суффиксы и персональные данные.
- Две области названы точно по заданию; типы нарушений допустимы для выбранной области.
- Поддерживаются несколько одновременных нарушений; норма, вероятность и список типов интерпретируются по документированным правилам.
- CSV содержит все восемь указанных полей и дополнительный `quality_prob`.
- Есть метрики по областям и типам с 95% интервалами и анализом ошибок.
- Есть batch API, ZIP-обработка, Docker, закреплённые зависимости и скрипт сборки/запуска для Linux/Unix.
- Веса поставляются с решением; инференс локальный, без внешних закрытых сервисов и передачи снимков.
- Время исследования не превышает 3 минут на целевой конфигурации; решение не требует объединения двух H200 из разных виртуальных машин.
- README, руководство пользователя, инструкция развёртывания, описание обучения и презентация позволяют провести финальную проверку без участия команды.

# Приложение: аудит данных и исследовательское обоснование

Дата исследования: 21 сентября 2026. Горизонт: 8 дней. GPU доступен, медицинского эксперта в команде нет. Состав команды и модель GPU пока неизвестны. Это исследование и план; обучение, инференс имеющихся весов и разработка приложения не выполнялись. Первое место нельзя гарантировать без знания соперников и формулы итогового балла.

## 1. Рекомендация

Строить локальный сервис контроля качества с двумя взаимодополняющими механизмами: предобученная модель распознаёт нарушения, геометрический модуль измеряет конкретные признаки и объясняет результат. Основное преимущество — корректная работа с реальными данными, проверяемые измерения, отсутствие утечек и полностью воспроизводимая сдача.

Базовая архитектура: DICOM → нормализация с сохранением геометрии → определение области и стороны → специализированные головы качества позвоночника/бедра + геометрические признаки → согласование результатов → CSV и визуальный отчёт.

Начать с DINOv2 ViT-B/14 с замороженными весами и небольшими классификаторами. Сравнить с компактной CNN на ImageNet. DINOv3 — дополнительный кандидат, если веса быстро доступны. Окончательный выбор определяется валидацией, а не новизной модели. Сложная сегментация, дополнительные датасеты и ансамбль допускаются только при измеримом улучшении.

## 2. Что установлено по локальным файлам

Исследованы `4.md`, все сохранённые ячейки `classifaer_learning.ipynb`, метаданные тензоров `model_classifaer.pth`, таблица `data/разметка.xlsx`, метаданные и пиксельные массивы всех DICOM. Дополнительно визуально просмотрена выборка из 16 снимков; полноценная медицинская ревизия всех изображений не проводилась.

### Объём и повторы

- 100 папок исследований и 100 строк исследований в Excel.
- 499 DICOM-файлов, но только **252 различных пиксельных массива с учётом формы**. Остальные 247 файлов повторяют изображения.
- 127 групп повторов. Точных совпадений пикселей между разными папками исследований не найдено. Близкие, но не идентичные изображения отдельно не проверялись.
- После устранения точных повторов: 74 исследования по 3 изображения, 4 по 2, 22 по 1.
- Все 499 файлов удалось декодировать. Это подтверждает чтение текущего набора, но не гарантирует поддержку всех вариантов закрытого теста.

Следствие: случайное разделение файлов недопустимо. Повторённый снимок может оказаться одновременно в обучении и валидации. При обучении следует исключить повторный вес дублей; при инференсе сохранить строку результата для каждого входного файла, если именно этого требует контракт организаторов.

### Метаданные

- Все файлы: GE Healthcare Lunar Prodigy Advance, CR, MONOCHROME2, 8 бит, один канал, несжатый Implicit VR Little Endian.
- В текущем наборе нет PixelSpacing, ImagerPixelSpacing и PixelAspectRatio. Нет полезных значений BodyPartExamined, Laterality и ViewPosition.
- Нет приватных DICOM-элементов и элементов overlay в проверенных файлах. На 16 просмотренных изображениях нет видимой разметки ROI.
- StudyInstanceUID и SOPInstanceUID присутствуют. SOPInstanceUID уникальны для всех 499 файлов.
- Значения `study` в Excel соответствуют именам папок, **но не StudyInstanceUID внутри DICOM**. Между папками и фактическими StudyInstanceUID проверено взаимно однозначное соответствие.
- PatientID одинаковый во всём наборе: использовать его для группировки пациентов невозможно.
- При чтении некоторых метаданных библиотека предупреждает о нарушениях формата UID и длины строк. Нужна терпимая обработка с журналом предупреждений; входные идентификаторы нельзя незаметно заменять в итоговой таблице.

Следствие: нужен явный манифест «строка Excel → папка → StudyInstanceUID → SOPInstanceUID → область → сторона → хеш пикселей». В отчёт выводить UID из DICOM. Имена папок использовать только для связывания учебной разметки, не как признаки модели. Study-группировка предотвращает утечку внутри исследования; отсутствие надёжного идентификатора пациента оставляет ограничение для повторных исследований одного человека.

### Распределение экспертных меток

Здесь считаются размеченные пары «исследование–область/сторона», а не DICOM-копии.

| Признак | С нарушением | С заполненной меткой |
|---|---:|---:|
| Укладка позвоночника | 6 | 99 |
| Ось позвоночника | 10 | 99 |
| Предметы/артефакты позвоночника | 17 | 99 |
| Позиционирование правого бедра | 17 | 72 |
| ROI правого бедра | 3 | 72 |
| Позиционирование левого бедра | 19 | 78 |

Итого 249 заполненных итоговых оценок областей: 73 положительных и 176 отрицательных. Это ещё не 249 подтверждённых соответствий конкретным уникальным изображениям: сопоставление надо завершить до обучения. Пустые ячейки не означают норму.

Найдены три противоречия между итогом позвоночника и логическим OR признаков, номера строк Excel:

- 8: признаки 0/0/0, итог 1, комментарий «сколиоз».
- 13: признаки 0/0/0, итог 1, комментарий «Сколиоз, не верня разметка».
- 37: признаки 0/1/0, итог 0, комментарий «перелом».

Без эксперта нельзя молча исправлять эти строки. Сохранить исходные метки, запросить трактовку организаторов и отдельно показать чувствительность результатов к этим случаям. Наличие патологии само по себе не равнозначно техническому браку исследования.

### Ноутбук и веса

Сохранённый ноутбук содержит 12 ячеек, чтение данных, список из 24 ручных меток и начало подготовки ResNet18. Нет сохранённого цикла обучения, разбиения, измеренных метрик и завершённого инференса. Путь данных в нём отличается от текущего. Список меток привязан к порядку обхода файлов, а не к устойчивым идентификаторам. Комментарии `taz/hip` не устанавливают однозначное соответствие двум требуемым классам.

Есть конкретное расхождение архитектур: в ноутбуке первый слой заменён на 1 входной канал, а в сохранённых весах `conv1.weight` имеет форму 64×3×7×7; `fc.weight` — 2×512. Следовательно, ноутбук в текущем виде не воспроизводит архитектуру чекпойнта. Проверялись метаданные архива весов, не качество предсказаний. Число эпох по нему не подтверждено.

Имеющийся классификатор стоит сохранить как кандидат для маршрутизации. В первый день восстановить точную архитектуру, предобработку и порядок классов; проверить на отложенных исследованиях. Высокая точность различения анатомии не доказывает качество определения нарушений.

## 4. Архитектура обучения

### Данные и предобработка

Сначала визуально сопоставить 252 уникальных изображения с областью и стороной. Сторона не нужна в финальном anatomical_region, но нужна для корректного присоединения правой/левой экспертной метки. При сомнении не угадывать по номеру файла; использовать проверяемое визуальное соответствие и отмечать неуверенность.

Сохранять оригинальный массив и параметры каждого преобразования. Масштабирование для сети — с сохранением пропорций и дополнением полей, без вырезания анатомических краёв. Поле кадра само является диагностическим признаком качества. Ветка для измерений должна работать в исходной или физически откалиброванной системе координат.

Для текущих 8-битных снимков сравнить простое приведение диапазона и мягкую нормализацию контраста. CLAHE — отдельная абляция, а не обязательная обработка. Повышение размера до 448/518 пикселей не создаёт новую информацию. Конкретное разрешение выбирать под энкодер и по эксперименту.

В загрузчике предусмотреть другие допустимые DICOM-представления. Modality LUT/rescale применяется перед VOI/windowing, если соответствующие преобразования присутствуют — это описано в [документации pydicom](https://pydicom.github.io/pydicom/stable/reference/generated/pydicom.pixels.apply_windowing.html). Проверять MONOCHROME1, пустые/константные кадры, отсутствие пикселей и поддерживаемые transfer syntax.

### Выходы модели

Для позвоночника: отдельная бинарная оценка общего качества и три sigmoid-выхода нарушений. Для бедра: бинарная оценка и два sigmoid-выхода. Правое и левое бедро обучать совместно после согласованного отражения, сохраняя преобразование для визуализации.

Использовать masked loss: неизвестные метки не участвуют в соответствующей функции потерь. Начать с взвешенной BCE, умеренной регуляризации и ранней остановки. Focal loss проверять только как отдельную гипотезу: при шумных метках она может усиливать обучение на ошибках разметки. Не использовать одновременно агрессивные веса классов и агрессивный oversampling без проверки.

Бинарная голова нужна в том числе из-за несовпадения итоговых и частных меток. Не вводить жёсткое равенство quality_class = OR(violation_type) до уточнения этих случаев. Хранить сырые вероятности отдельно; окончательное согласование проводить по опубликованной политике. Не выдумывать тип нарушения, чтобы объяснить положительный бинарный ответ. Контракт для случая «нарушение вероятно, тип неуверенный» согласовать с организаторами.

План экспериментов ограничить:

1. Простая CNN с предобучением ImageNet как воспроизводимый ориентир.
2. Замороженный DINOv2 и регуляризованные головы.
3. Осторожное дообучение последних блоков лучшего энкодера.
4. Добавление измеримых геометрических признаков.
5. Один дополнительный энкодер — DINOv3 или RAD-DINO.
6. Усреднение двух лучших моделей только если их ошибки различаются и общий результат улучшается.

Для каждой строки эксперимента сохранять одинаковые группы разбиения, метрики, время, параметры и список ошибок. Не проводить десятки незапланированных подборов по 100 исследованиям.

## 5. Измеримые критерии и отсутствие эксперта

### Ось позвоночника — первый геометрический модуль

Разметить небольшой пилот из 20–30 учебных снимков: несколько точек вдоль центральной линии и признак уверенности в каждой точке. Если схема воспроизводима, расширить примерно до 60–80 снимков. Это техническая разметка видимой геометрии, не новая экспертная оценка качества. Если в команде несколько человек, разметить часть независимо; если один — повторно с временным интервалом. Сомнительные структуры пропускать.

Обучить компактную модель ключевых точек или маски позвоночника. По устойчиво найденной линии измерять общий угол к вертикали. Отдельно хранить кривизну, не называть её автоматически нарушением укладки.

В задании задано 1,05 мм по Y и 0,6 мм по X, но в файлах масштаб отсутствует. До подтверждения организаторов эти значения — явно отмеченное предположение. При подтверждённом масштабе угол от вертикали вычислять из физических смещений: arctan(|Δx × sx| / |Δy × sy|). Нельзя измерять угол после произвольного растяжения в квадрат. Нужно выяснить, как организаторы измеряли свои примеры угла.

При уверенной геометрии сравнивать с порогом 5° из задания. При неуверенной локализации не выдавать точные градусы как достоверное измерение; использовать классификационную ветку и отметку для ручной проверки.

### Укладка и артефакты позвоночника

Для охвата кадра проверять видимость нужных ориентиров и их отношение к краям. Идентификация Th12 при переходных позвонках сложна без специалиста: не создавать фиктивную точную разметку. В таблице уже есть комментарий о L6/люмбализации, поэтому нельзя просто считать позвонки от края.

Артефакты: основная классификационная голова, при возможности грубые прямоугольники вокруг очевидных объектов. Grad-CAM допустим как карта внимания, но не как подтверждённая маска предмета. Порог по яркости сам по себе недостаточен: кость также яркая.

### Бедро

Объединить 150 размеченных случаев обеих сторон. Голова укладки учится по организаторским меткам; добавлять признаки формы малого вертела только после проверки устойчивости его локализации. Отсутствие видимого малого вертела может быть связано с несколькими причинами; не задавать произвольный медицинский порог без основания.

Для ROI сначала выяснить, что требуется измерять. Дано «без разметки», однако требуется проверять корректность разметки. Исходные контуры ROI в просмотренных снимках не видны, приватных тегов/overlay нет. Можно оценить достаточность поля обзора и предложить область, но это не доказывает корректность неизвестной исходной ROI.

После уточнения определять необходимые анатомические ориентиры и расстояния до краёв. При подтверждённом исходном масштабе 30 мм по Y соответствуют примерно 28,6 пикселя, 20 мм по X — 33,3 пикселя. Эти значения неприменимы автоматически к уже изменённому размеру или иной геометрии экспорта. С семью положительными ROI-примерами основной шанс — простая проверяемая геометрия вместе с классификатором; сложный отдельный глубокий классификатор легко переобучится.

### Аугментации

Допустимы умеренные изменения яркости/контраста, слабый шум, отражение бедра с преобразованием меток и координат. Любые повороты, сдвиги и обрезки могут менять правильный ответ: их нельзя применять со старой меткой качества. В частности, поворот на 10° создаёт нарушение оси, а crop может удалить обязательную анатомию.

Синтетические дефекты проверять отдельно и только внутри учебного фолда. Геометрическое преобразование должно менять соответствующую метку по проверенному правилу; другие затронутые метки нельзя автоматически оставлять прежними. Синтетическая вставка металла не заменяет реальные артефакты. Финальная оценка — только на настоящих исходных снимках.

## 6. Валидация, которой можно доверять

Основное разбиение — 5 групповых фолдов по исследованию с приближённым балансом нарушений. Проверить наличие редких положительных случаев в каждом фолде; если для объединённых групп это невозможно, уменьшить число фолдов. Все снимки, стороны, дубли и синтетические варианты одного исследования остаются вместе.

Получать out-of-fold вероятности: каждый реальный снимок оценивается моделью, не видевшей его исследование. Маски, псевдометки, калибровка и обучение геометрии также должны соблюдать границы фолдов. Разметка точек на валидации допустима для оценки локализации, но её нельзя использовать для обучения соответствующей модели.

Основные метрики: бинарные F1 и ROC-AUC в целом и по области, macro-F1 типов, sensitivity/specificity, PR-AUC редких ошибок. Для ROI показывать число найденных положительных примеров и false positive, а не только красивый процент. Считать результаты на уникальных изображениях и отдельно в формате файлов, ожидаемом организатором: повторы не должны скрывать слабое качество.

Пороги и веса ансамбля выбирать на внутренних разбиениях обучающих групп. Если ради срока они выбраны по общим OOF-предсказаниям, прямо назвать эту оценку пригодной для разработки, но потенциально оптимистичной. Для финальной оценки замороженной процедуры предпочтителен вложенный групповой протокол; минимум — отдельно измерить влияние настройки порогов.

95% интервалы получать бутстрэпом исследований, сохраняя внутри все связанные изображения. При слишком малом числе положительных классов интервалы будут широкими; bootstrap без одного из классов не использовать для AUC без явного учёта невалидных повторов. Интервалы не устраняют оптимизм выбора лучшей модели по той же валидации.

Отдельный анализ: три противоречивые строки, пограничные углы, артефакты, эндопротезы, подозрительная анатомия, отсутствующие метки, ошибки маршрутизации. После выбора финального протокола обучить сдаваемые веса на всех допустимых учебных данных или использовать ансамбль фолдов; опубликованные метрики брать из валидации, не из обучения.

Если команда больше: распределить ответственность между данными/ML, геометрией и сервисом/демонстрацией, используя один манифест и одинаковые фолды.

### Условия прекращения экспериментов

- Нет пригодных внешних данных после короткой проверки доступа — отказаться от внешнего датасета.
- Геометрические точки не размечаются воспроизводимо — упростить схему; не делать их жёстким правилом решения.
- Дополнительная модель не даёт устойчивой пользы по фолдам — исключить её.
- К концу дня 4 не решена трактовка ROI — сохранить обучаемую ветку по исходным меткам, явно обозначить границы объяснения и продолжить обязательный сервис.
- В день 5 заморозить архитектуру. Последние три дня защищают результат от провала на автономном запуске.

## 8. Продукт и сдача

Обязательное: оба anatomical_region с точными строками из задания, все пять допустимых типов нарушений с привязкой к области, поддержка нескольких одновременных нарушений, бинарный класс и quality_prob, время и processing_status, одна строка по согласованной единице учёта, batch API, ZIP, Docker, веса внутри поставки, закреплённые зависимости.

Низкая уверенность модели не равна техническому Failure. Для неё предусмотреть дополнительную отметку ручной проверки, продолжая выдавать обязательный результат по зафиксированным порогам. Failure — ошибка обработки; недостающие поля при невозможности прочитать DICOM оформлять по согласованному контракту, не подделывать UID.

Проверить: переименованные файлы, иное расположение каталогов, одиночное изображение, повторы с разными SOPInstanceUID, битый DICOM, посторонний файл в ZIP, пустой пакет, пути с кириллицей, повторный запуск, ограничение времени, безопасную распаковку, работу без сети. Классификация не должна зависеть от суффикса файла, имени папки или персональных тегов.

Две H200 по заданию находятся в разных виртуальных машинах. Не рассчитывать на общую память 282 GB или обязательный распределённый инференс. Базовый сервис должен работать на одной GPU. Точную минимальную конфигурацию, скорость и память определить измерением; инженерная цель — заметно быстрее лимита 180 секунд на исследование с учётом чтения и экспорта.

Демо: загрузка архива → очередь исследований → исходный снимок → список нарушений с уверенностью → ось/ориентиры/границы и измерение → скачивание CSV. Для геометрических ошибок показывать конкретное измерение и порог; для классификационных — вероятность и осторожно обозначенную карту внимания.

Главные дополнительные функции по ценности: визуализация измерений, понятный просмотр ошибок, пакетный экспорт. DICOM SR и подтверждаемая коррекция разметки — только после готовности обязательного контура. Автоматическое преобразование картинки не должно выдаваться за исправление физической укладки пациента.

Защита: постановка задачи; аудит 499 → 252 и предотвращение утечки; выбранная архитектура; сравнение baseline/энкодера/геометрии/ансамбля; метрики с интервалами и количеством случаев; честные ошибки; локальная демонстрация; ограничения и план экспертной проверки. Числа измерений в демонстрации должны быть реально получены моделью, не вставлены вручную.
